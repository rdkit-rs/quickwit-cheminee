Independent design recommendation against `c15204119d29285511ac1a5563732a6a714a3315`, 2026-10-16. **Fix timestamp cutoff quantization and unknown-bound handling together before claiming timestamp-sorted top-K correctness.** This is a read-only source review and a mathematical counterexample; it is not a new HTTP reproduction. No source changes were made.

`quickwit/quickwit-indexing/src/models/split_attrs.rs:97` writes both split endpoints using `DateTime::into_timestamp_secs()`. The pinned Tantivy revision `057458b`, `common/src/datetime.rs:102`, implements that conversion as `timestamp_nanos / 1_000_000_000`, truncating toward zero. Date sort values remain signed nanoseconds (`quickwit-search/src/collector.rs:195`).

`quickwit-search/src/leaf.rs:1515` instead rounds descending and trace cutoffs upward. Given a current worst top hit at +1.2 seconds, a pending split whose highest matching timestamp is +1.8 seconds has metadata end +1. The cutoff becomes +2, and `can_be_better` incorrectly rejects that split. With `CountAll`, the split can still contribute its count while contributing no hits: **an exact total does not prove correct top hits**. Both rounding comments in the current function describe the wrong direction of improvement.

The smallest coordinated fix is:

1. In `record_new_worst_hit`, convert signed nanoseconds using the same monotone quantization as the writer for both timestamp sort directions and the shared trace branch: `DateTime::from_timestamp_nanos(timestamp_ns).into_timestamp_secs()` (equivalently, signed division by one billion). Keep inclusive comparisons: descending `end >= cutoff`, ascending `start <= cutoff`. For monotone quantization q, any actual descending contender x >= t satisfies q(x) >= q(t); the ascending proof is symmetric. Equality must remain eligible for finer timestamp precision and secondary/document-address tie breakers. Do not change the metadata format, query AST, candidate domains or collector ordering.
2. Preserve unknown endpoints explicitly throughout `optimize_split_order` (`leaf.rs:1375`), upfront `optimize` (`:1395`) and dynamic `can_be_better` (`:1498`). The generated `timestamp_start()`/`timestamp_end()` accessors turn `None` into zero, which is unsafe evidence for pruning. Use private conservative views of start as negative infinity (`unwrap_or(i64::MIN)`) and end as positive infinity (`unwrap_or(i64::MAX)`), or equivalent explicit Option handling. A missing relevant endpoint cannot rule a split out. Unknown endpoints among the initial supposedly sufficient splits must also prevent an unjustified nonoverlap proof. Updating only the dynamic check leaves the MatchAll upfront path unsound.
3. Keep `simplify_search_request` (`:1655`) and its `CountAll`/aggregation retention rules intact. A split that cannot improve hits can still change requested counts or aggregation output; relevant errors must still propagate. Keep the `peek_worst_hit` capacity condition (`collector.rs:1281`), including `start_offset + max_hits`, so pruning cannot begin before enough hits exist. Do not broaden this patch into trace-aggregation skipping.

Toward-zero division is deliberate for negative timestamps: an ascending cutoff of -1.2 seconds must retain a pending -1.8-second hit whose metadata start is -1. Replacing ascending conversion with `div_euclid` would produce -2 and incorrectly prune it. Division by positive one billion also handles `i64::MIN` and `i64::MAX` nanoseconds without multiplication, addition, negation or overflow. This recommendation follows the verified current writer; changing split metadata to another quantization would require a separate compatibility review.

Use deterministic direct tests of `record_new_worst_hit`, `can_be_better`, `optimize` and `simplify_search_request`, then a multi-split fixture with distinct metadata endpoints and a constrained scheduler. Split processing is asynchronous; a passing all-at-once run may never execute the faulty cutoff. Ensure the later split is considered after the first result establishes the cutoff, and assert the fixture really has multiple splits. Cold and cached requests should agree. For pre-epoch/extreme HTTP values, use explicit RFC3339 input and nanosecond precision so date-unit inference or default storage precision cannot invalidate the oracle.

The patch is local to split eligibility and needs no global scan or chemistry verification change. Keep broader old-schema, OR relevance, durability and performance gates separate. The design can be accepted now; runtime correctness claims remain conditional on the focused native and HTTP regressions.
