# Ingest acknowledgement ambiguity review

Independent source review, 2026-10-16. Repository: `/workspace/quickwit-cheminee-pr3-inspection`, HEAD `1f847fef3e7cf3c9c20e6c38da47f62c71b9a4a1`. The five ingestion files hashed below had no working-tree changes when inspected. No repository files were edited and no tests were run for this review.

**Verdict: catalog promotion remains blocked by automatic replay of writes whose outcome is unknown.** The existing timeout correction is sound in scope, but Internal, Unavailable, several Persist failures, and missing acknowledgement entries still permit replay. The smallest useful correction is a conservative retry allowlist, complete acknowledgement accounting, and one producer classification fix. This prevents these server-side replays; it does not provide exactly-once HTTP ingestion, WAL durability, or a completed catalog/relevance/HA gate.

The WAL evidence is stronger than a hypothetical network race. `quickwit/quickwit-ingest/src/ingest_v2/mrecordlog_utils.rs:54` discards DocUid and passes `None` as the append position, so retrying the same DocBatch does not deduplicate it. The pinned mrecordlog source at `/workspace/recovery/cargo-native/git/checkouts/mrecordlog-f8da589da92ddadb/3b3562e/src/multi_record_log.rs:212` calls `write_record` then `persist_on_policy`, either of which can return an I/O error. Its atomic-batch documentation does not establish that an error means no complete record was written. In-memory and disk state can diverge on I/O error (its own comment at line 157).

Replication has the same acknowledgement problem. `replication.rs:371` maps both failure to enqueue and loss of the reply after enqueue to ReplicationError::Closed; its timeout does not undo an already sent request. `replication.rs:580` leaves a replica-position mismatch as TODO, so replay cannot rely on the replica rejecting a repeated batch. A lost replica acknowledgement can therefore lead to an omitted Persist result, a replayed replica append, and then the definite post-append leader Internal described above.

**Proposed bounded correction**

1. In `workbench.rs:386`, replace the blanket transient cases with an explicit allowlist: local NoShardsAvailable, typed Persist(WalFull), the proven pre-dispatch overload causes, and optionally Persist(NoShardsAvailable) only after step 2. None remains eligible for its first attempt. Every other failure is terminal. The existing shared persist deadline in `router.rs:454` and preservation of acknowledged successes should stay.

2. If remote NoShardsAvailable retries are retained, change only the replica `AppendDocBatchError::Io` classification at `replication.rs:640` from ShardClosed to existing `ReplicateFailureReason::Unspecified`, keeping its shard-close cleanup. This converts to terminal Persist(Unspecified) without changing the wire schema. Actual pre-append ShardClosed/ShardNotFound checks remain retryable. The replica QueueNotFound branch is a genuine local no-append case: the pinned WAL checks queue existence before writing, and the leader has not appended yet. The leader's QueueNotFound is different because its replica may already have appended. For mixed-version clusters, old replica I/O classifications remain ambiguous; either deploy the corrected image throughout the bounded test cluster or conservatively keep all remote NoShardsAvailable terminal.

3. In `router.rs:278`, reconcile each OK response against `PersistRequestSummary.subrequest_ids` before applying it. Validate returned leader identity, expected IDs, and one outcome per ID across successes plus failures. For an otherwise coherent response, retain explicit successes/failures and record terminal Internal for every missing expected ID. Do this even if the ID has an earlier WalFull/NoShardsAvailable failure. Duplicate, conflicting, or foreign IDs should make the submitted RPC's outcomes terminal Internal before mutating success counters or routing state; unrelated RPC results remain intact. This avoids both replay and `num_successes += 1` inflation (`workbench.rs:168`) or final result accounting panics. A success followed by a duplicate failure must never leave an apparent safe rejection.

4. Also make the ingester return an explicit terminal NodeUnavailable for every unresolved pending replication subrequest, instead of the `continue` at `ingester.rs:713`. A small implementation can collect already-reported failure IDs after the replication loop, then emit NodeUnavailable for each `!successfully_replicated` pending ID without a reported failure. This preserves successful siblings and avoids quadratic scans. Router reconciliation remains necessary as defense against incomplete/older peers. Record the actual replication error at `ingester.rs:677`; it is currently discarded.

5. Preserve the unknown outcome at the public boundary. Change `SubworkbenchFailure::Unavailable` mapping (`workbench.rs:347`) and Persist(NodeUnavailable) conversion (`quickwit/quickwit-proto/src/ingest/mod.rs:320`) to existing IngestFailureReason::Internal rather than NoShardsAvailable. Unknown and omitted results may use Internal as well. This requires no new protobuf/OpenAPI enum. The REST mapping in `quickwit/quickwit-ingest/src/error.rs:98` currently loses detail; a bounded log event with leader, subrequest IDs, original reason, and `outcome_unknown=true` is needed for diagnosis. Document that this error may follow a write and must not trigger blind catalog batch replay. An HTTP status alone is not an idempotency contract.

**Bounded regression tests and existing seams**

- Extend `quickwit/quickwit-ingest/src/ingest_v2/router_timeout_tests.rs:29`. Replace its timeout boolean with explicit injected outcomes, retaining the detached remote task at line 39. Inject append-then-Internal, append-then-Unavailable, typed NodeUnavailable, Unspecified, and a missing acknowledgement. Assert failure is returned, no later success overwrites it, exactly one persist call occurs, and all recorded DocUids occur once. For Unavailable, provision an alternate route/mock control-plane response so an accidental retry would really append again instead of merely failing on an unexpected mock call.
- Add a separate early transport-failure case whose detached append completes after the router has returned. Advance paused time and assert one eventual append, no second RPC. Keep the existing late deadline test (`router_timeout_tests.rs:150`), slow valid acknowledgement test (line 137), and returned Timeout test (line 165).
- Exercise response accounting through `process_persist_results`: one acknowledged success plus one omitted ID; omission after a prior safe rejection; duplicate success; success/failure conflict; foreign ID; wrong leader. Check no panic, no replay, exact final success/failure coverage, and preservation of unrelated acknowledged successes.
- Positive controls must still retry a proven pre-write WalFull (with a second route), a pre-write NoShardsAvailable after the producer fix, and known circuit-breaker rejection. Assert two attempts but one append. Existing retry setup is in `router.rs:1446`; extend it with an append ledger/call counts.
- Use the real leader/follower fixture `test_ingester_persist_replicate` at `ingester.rs:2384`. Wrap the follower ACK stream to drop or delay the ReplicateResponse after the real follower append. Its leader response must contain one explicit unknown failure per unresolved subrequest and no replay. Inspect both WALs using the existing `mrecordlog.assert_records_eq` seam. The stream channels in `replication.rs:997` already provide timeout/closed-reply control. This test proves the producer path, while the router ledger tests prove policy.
- Update the replica I/O classification assertion in `replication.rs:1573` and leader tests at `ingester.rs:2327,2376`. Existing `ingester:append_records` failpoints (`mrecordlog_utils.rs:65,79`) fire **before** append; they test failure classification/cleanup, not append-then-lost-ack. Do not cite them as evidence of post-append safety. If adding a post-append failpoint, run its global failpoint test in isolation; a per-test ACK-stream wrapper avoids that shared-state concern.
- Add enum-mapping/allowlist coverage and one REST boundary assertion that an ambiguous NodeUnavailable/transport failure is not reported as the retryable no-shards rejection. Run affected workbench, router, ingester, and replication tests; no native chemistry rebuild is needed for these tests.

For catalog refresh, even after these checks pass, an unknown acknowledgement must quarantine the staging generation. Do not replay that batch into the same generation, promote a count observed while an append may still complete, or claim exactly-once ingestion. Start a new unique generation from the frozen complete snapshot; keep the active generation unchanged until the new candidate is fully audited. This review does not assess or approve generation promotion/CAS implementation.
